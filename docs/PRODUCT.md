# A useful app should not require a cloud education

**Built for humans. Operated by AI. Owned by you.**

Unforge aims to help people make software without inheriting a development platform they cannot understand or leave. Git provides portable source history. The product adds understandable local operations and an interface that authorized coding agents can also use.

## Problems to solve

| Beginner's problem | Product response | Alpha boundary |
| --- | --- | --- |
| “I have an idea but do not know how to explain it to a developer.” | Save a plain-language request beside the project, ready for the person's chosen agent. | File handoff works independently. Optional Codex execution uses the person's existing configured CLI and account; a live README-edit smoke test covered the proposal-to-export path, not general AI quality. |
| “I am afraid of losing the version that worked.” | Save described versions and restore an earlier state without erasing history. | Restore requires saved work and affects project files, not external events or databases. |
| “I do not know what all these provider names mean.” | Present evidence from recognized configuration and dependency files, with a concrete next question. | A source reference does not prove a live account, service, or bill. |
| “I wanted a small personal tool and ended up with cloud infrastructure.” | Compare local, on-demand, and managed approaches against availability needs. | Comparisons are descriptive candidates, not pricing quotes or automatic migrations. |
| “What happens if I stop using this product?” | Keep ordinary Git repositories and export committed history in a standard bundle. | The bundle does not include uncommitted files or external application data. |
| “A technical interface makes me feel like I cannot do this.” | Use actions such as save a version, restore, and export; retain paths and Git details when useful. | The current interface still requires basic software installation. |

## The dependency footprint

The offline analyzer examines only supplied text. It recognizes named hosting manifests, GitHub workflow files, selected dependency names inside parsed package manifests, and limited configuration markers. Evidence gives file paths and line numbers without reproducing configuration values.

A positive Fly machine minimum is a reason to inspect deployed settings, not proof that a machine exists or incurs a particular charge. A scheduled workflow is a source configuration observation, not evidence that it is active. A provider SDK can be unused or connected only in development.

The three architecture candidates explain where each may fit and what responsibilities remain. They deliberately do not invent dollar amounts. Reliable cost advice requires live configuration, usage, current pricing, and the owner's availability requirements—none of which an offline source scan establishes.

## Ownership as an acceptance criterion

An improvement should leave the project more understandable and portable. The user should be able to identify where files live, which actions change history, what depends on an external service, and how to leave. The core should not require our own servers to keep running.

Provider independence does not mean every application can run free or offline. Continuous availability, shared data, messaging, and model inference may require additional services. Explain that requirement before adding it, and preserve an exit path where feasible.

## What comes next

Measure whether beginners can complete real tasks without technical intervention. Expand supported import, agent, and deployment workflows only when they preserve unrelated work and produce reviewable results. Portable collaboration and durable personal customization remain roadmap work; the alpha does not claim to replace every GitHub capability.
